# Scope the local execution model per profile, and anchor it to the host's free memory

**Status:** accepted

The local stack is the only environment where every correctness claim is actually evidenced, and the whole stack does not fit on the host: 12 CPU and 14 GiB total with roughly 7.5 to 8 GiB free, against fourteen components. So a profile's entitlement has to be **declared** rather than inherited, and this decision fixes how. Each profile is a **resident set** plus a **transient list**, and its budget is the peak: the sum of the resident ceilings plus the largest single transient ceiling. The alternative, a budget that sums every service a profile could ever start, is unsatisfiable by construction once ClickHouse is included, because ClickHouse's documented default is not a fixed allocation but a ceiling of 90% of available memory, which alone is 6.3 to 7.2 GiB here. The peak model is what lets a profile declare a real entitlement for the two services that need room, ClickHouse and Flink, instead of shaving every ceiling to nothing so an arithmetic sum fits.

The **anchor is the host's declared free memory**, not the cloud. ADR-0027 already fixed the cloud node shapes, and the ticket that produced this decision forbids re-litigating the cloud topology, so the cloud arm is an input that is checked against the per-service table rather than a quantity derived from it. One per-service table carries a `local_ceiling` and a `cloud_limit`; the local column is what the preflight enforces, the cloud column is checked to fit the node groups. The recorded consequence is that the local peak of 7168 MiB is about 44% of the minimal arm's 16 GiB, so a local run evidences the shape of the entitlement and never the cloud capacity.

**When the host cannot hold a profile, the run refuses rather than degrades.** If free memory is below the declared peak plus a 512 MiB reserve, the preflight refuses and names the shortfall. Between 7.0 and 7.5 GiB free it offers the profile's declared reduced variant, which is the same ceilings with the observability overlay dropped, and the run is labelled as reduced in its evidence item. The consequence is written into the register rather than left to be inferred: no alert drill can be produced from a reduced run, so the incident-laboratory items are not evidenced there.

## Considered options

- **A budget that sums every service in the profile.** Rejected: it forces ClickHouse under 1 GiB in both paths, which is where the budget stops being a budget and becomes a fiction, and it counts run-to-completion members like `spark-submit` as if they were resident alongside everything else.
- **Splitting the profiles until the sums fit.** Rejected: the ticket that produced this decision explicitly does not re-litigate the profile set, and the profile list is load-bearing for the completion bar's reproducibility definition.
- **Anchoring on the cloud minimal arm (16 GiB).** Rejected: the local run would then be exercising 47% of its own anchor, which makes the anchor a description of a different machine rather than the constraint the budgets are built to.
- **Anchoring on host total memory (14 GiB).** Rejected: not available to a profile, since the operating system and the desktop already hold the difference.
- **Refusing outright, with no reduced variant.** Rejected: it makes the streaming path unrunnable at the bottom of the host's stated free-memory range, where the alternative costs only the observability overlay and is honestly labelled.
- **A soft or advisory budget.** Rejected: a ceiling that is not enforced proves nothing, and the whole point of declaring one is that a service which exceeds it is killed and the run is judged to have failed its budget.

## Consequences

The entitlements live in `deployment/budgets/profiles.yaml` and the reasoning in [the local development document](../local-development.md). Six ceilings sit below a documented default or recommendation and each requires an explicit override, collected in the register so the deviation is visible: Kafka's heap falls from 1 GiB to 512 MiB, Debezium Connect's from 2 GiB to 384 MiB, ClickHouse's from a 90%-of-available ceiling to 1024 or 1792 MiB, Flink's two process sizes are set where they have no default at all, Spark runs in local mode on one JVM, and Grafana sits below its published 512 MB recommendation because the platform does not use image rendering.

Three limitations follow and are recorded rather than discovered later. **There is no CPU floor anywhere**, because neither named provider enforces a CPU reservation outside swarm, so a service on a busy host can be starved with no guarantee. **A ceiling is a hard limit**, so an exceedance is an OOM kill and the run's assertion phase has to surface it as a profile-budget failure rather than as an application bug. And **the entitlements are not thresholds**: they live in their own register, because admitting them to `docs/budgets.yaml` would let a resource ceiling be cited as the threshold a measurement is judged against, which is the confusion the completion bar's honesty rule exists to prevent.

The portable compose subset changes as a consequence. It now admits `deploy.resources.limits.cpus`, `.memory` and `.pids` and nothing else of `deploy`, verified in both providers' source rather than in documentation, because the Deploy Specification is optional and a conforming provider may ignore the whole block. `memswap_limit` stays rejected as Docker-only. And the ban on `depends_on` with `condition` is restated: it is a resilience choice, not a portability constraint, because both providers implement the condition and a self-retrying service also survives a dependency that later restarts.
